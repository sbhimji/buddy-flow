# Mini-spec 1.2 — Live feeder & capture to disk

Status: **open** (written 2026-08-13). Story: DEV-PLAN Phase 1 → 1.2.
Includes the live websocket feeder moved here from 1.1 (capture-before-parse
lives inside the socket read loop; no live run may precede capture).

## What

One websocket connection to `wss://socket.massive.com/stocks` carrying both
channels (`T.<sym>` + `Q.<sym>`) for the 189 universe symbols. The read loop
does exactly two things with each raw frame, in order:

1. **Append to capture** — raw bytes as received, before any decode, so a
   parser fault can never lose data and the archive records the wire, not our
   interpretation of it (the vendor client's structs drop `pt`, which is why
   we don't capture decoded structs).
2. **Decode and submit** — parse the JSON event array, scale ms→ns, resolve
   symbol → `*SymbolState`, submit to the 1.1 pipeline. Status/control events
   are captured but not submitted.

Replay of captures (`cmd/ingest -capture`) feeds raw frames through the SAME
decode path — replay exercises the real decoder, which the CSV path never did.

## Capture format

- Directory per session: `data/capture/<YYYY-MM-DD>/` (gitignored).
- `stream.jsonl`: one record per frame, `<receive_ns> <raw frame>\n`.
  Frames are JSON (no raw newlines), so the format stays greppable. Receive
  timestamp is wall-clock epoch ns (feeds the 1.5 clock-drift metric).
- Everything on the wire is captured: auth responses, subscribe acks, status
  and error frames. Our own control records use the same line format with a
  synthetic frame `[{"ev":"_capture","event":"connect|disconnect|reconnect|
  start|stop",...}]` so replays see gaps explicitly rather than inferring them.
- Plain text during the session (live gzip would lose its buffer on a crash);
  bounded flush cadence (≤500ms of unflushed data). Compress at session end —
  manual/one-liner for now, a nightly job owns it later (with the S3 offload).
- `manifest.json` written on clean close: date, start/stop ns, frame/byte
  counts, subscription list, universe size. An ungraceful kill leaves no
  manifest — that absence is itself the integrity signal (1.5).
- The reader tolerates a torn final line (power loss mid-append costs one
  frame, never the session).

## Design constraints

- Library: gorilla/websocket, not the vendor client (which hides raw frames
  and drops `pt`). Auth/subscribe protocol spoken directly: send
  `{"action":"auth","params":<key>}`, await `auth_success` status, then
  subscribe in chunks. Key from `MASSIVE_API_KEY` (env or `.env`).
- Reconnect on socket error: capped exponential backoff, resubscribe,
  disconnect/reconnect control records around the gap. Until the failover
  feed exists (6.1), a gap is honest data loss — next-day flat-file
  reconciliation quantifies it.
- Websocket timestamps are ms; scale ×1e6 at decode (ns is canonical —
  mini-spec 1.1 / types.go).
- Capture is unconditional: `cmd/capture` has no flag to disable it.
- Decode cost is off the floor path: live rates (68k/s measured burst) are
  ~6× below the replay-proven pipeline rate; stdlib JSON is fine until 1.5
  metrics say otherwise.

## Done when

1. A live session (partial is fine for first blood — after-hours counts)
   captured to disk with manifest.
2. That capture replayed through the pipeline **twice**: identical message
   counts and identical final NBBO state. (DEV-PLAN's "identical bucket
   outputs" phrase belongs to 1.4 — buckets don't exist yet; amendment noted.)
3. Kill-safety: capture process killed ungracefully mid-session → restart
   appends to the same session directory, reader tolerates the torn tail,
   gap control records present, replay still runs.
4. Live counts vs next-day flat file reconciliation run once, delta
   *reported* (not gated — TRF/late-print timing means the normal delta is
   unknown; measuring it is the point; 1.5 owns the permanent nightly check).
