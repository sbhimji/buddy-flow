# Mini-spec 3.0 — Developer view (build first)

Status: **open** (written 2026-08-15). Story: DEV-PLAN Phase 3 → 3.0.

## What

A crude auto-refreshing **terminal** table: one row per basket (all 22, full
membership), one column per metric, fed by capture replay now and by the live
session later. No design work — numbers only. This is the learning
instrument; its real deliverable is the **scaffold**: a metric-column
registry such that each Phase 3 story adds its column the day the metric is
written, touching nothing but the registry.

## Decisions (settled in discussion 2026-08-15)

- **D1 — Home & seam.** New `internal/devview`. The view wraps the 1.4
  `bucket.Store` and implements `ingest.Observer`: `ObserveTrade/Quote`
  delegate to the store and track the replayed clock (max SIP ts) — nothing
  else. **Pull model:** all metric math happens at render time, reading the
  store and the 2.1 profiles; observers aggregate, they never calculate
  (the hot path is the pipeline's single consumer goroutine).
- **D2 — Feeds.** `cmd/replay -view`, valid with `-capture` only — flat-file
  replay streams trades and quotes concurrently with meaningless cross-feed
  order, so a "current time" is a lie there. Pacing is the existing `-speed`
  flag: paced replay is the watching instrument; instant replay renders once
  at the end (and is what the snapshot test uses). `cmd/live` wiring is
  deferred to the first live run — the view is feed-indifferent by
  construction (it's an Observer), but how it coexists with live log output
  is a Monday question, not a guess.
- **D3 — Clock & refresh.** A render loop on a wall-clock ticker re-renders
  when the *replayed* clock has advanced ≥1s (well inside the ≤5s
  print→pixel budget); one final render after the pipeline drains. The
  renderer itself is pure — `Render(atSec) → string`, no ANSI, no wall
  clock — screen clearing belongs to the command. Purity is what makes the
  snapshot test byte-exact.
- **D4 — Day-one columns**, honest about what exists post-2.2: basket name,
  `N` member count, `$last` counted $vol of the last **completed** minute,
  `base` matched-minute baseline $vol for that same completed minute (sum
  of member profile median dollars — the read-time-sum invariant), `rvol`
  their ratio (a gap when the baseline is 0 or the minute is outside the
  regular session), and `$now` accumulating in the current minute.
  `$last`/`base`/`rvol` all describe the same completed minute — the header
  line names it explicitly (renamed from `$m-1`/`$cur` 2026-08-16: the
  pairing was ambiguous) — because a partial minute against a full-minute
  baseline reads falsely low. **No z column**: a basket σ cannot be
  honestly derived by summing member σs; FlowShareZ is 3.1's story and
  lands as a registered column. Counted = `profile.Counted` (one policy
  source).
- **D5 — Registry.** A column is a name plus a cell function of (render
  context, basket row). Adding a metric = appending a column; renderer and
  commands untouched (acceptance-tested with a dummy column).
- **D6 — Rows.** Baskets only (benchmarks are not rows), sorted by name —
  deterministic, and a watcher can find a basket without chasing it around
  the screen. Ranking/sorting by activity is display work (Phase 5), not 3.0.
- **D7 — New narrow APIs.** `universe.LoadBaskets` (basket name + members,
  sorted, same config; `Load` unchanged) and `bucket.Store.Window(state,
  fromSec, toSec)` (value-copy sum of 1-second buckets under the store
  mutex — the "future dev view" reader the store doc already promises).
- **Rendering discipline.** Statements of measurement only — no buy/sell
  language, no interpretation, no color (Glow is 3.8; palette is D10).

## Done when (all on replayed recorded data)

1. The table renders and updates through the replayed 2026-08-14 capture,
   all 22 baskets populated. Capture reality: 08-13's capture is an evening
   smoke run and 08-14's starts 11:51 ET — no capture on disk covers the
   open, so the open-minute watch happens on the first Monday capture; until
   then this criterion verifies on the covered afternoon. `-view-at
   HH:MM:SS` additionally renders the table as of any past second after the
   replay — buckets are event-time keyed, so the post-hoc render is exact;
   it is how done-when #3's spot check reads the table.
2. Snapshot determinism: rendering at a fixed second after an instant replay
   is byte-identical across two runs (unit-tested on a synthetic store; the
   CLI run on the real capture checked by hand).
3. Spot check: one basket at one minute — completed-minute $vol and baseline
   agree with hand computation from the bucket file and profile CSVs.
4. A dummy column registered in a test appears in output with no renderer or
   command changes.
