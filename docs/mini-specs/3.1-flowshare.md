# Mini-spec 3.1 — FlowShare & FlowShareZ [F4, A8]

Status: **open** (written 2026-08-16). Story: DEV-PLAN Phase 3 → 3.1.

## What

The money-flow metric (§2.1 — the product's core claim):

    FlowShare(B,t)  = counted $vol(members of B, minute t) / counted $vol(universe, minute t)
    FlowShareZ(B,t) = zguard.Z(FlowShare, μ20d(B, matched minute), σ20d(B, matched minute), floor)

plus the A8 concentration stat (top member's % of basket $vol, with symbol).
All three render as registered dev-view columns. Counted = `profile.Counted`
(one policy source). This is the first z in the system — the metric F13's σ
guard was built for.

## Decisions (settled in discussion 2026-08-16)

- **D1 — Denominator = basket members only.** The union of the 164 distinct
  basket members, each symbol counted once; benchmarks (SPY/QQQ/TLT/BIL/
  sector ETFs) are excluded — an SPY volume burst must not crush every
  basket's share simultaneously. **This amends §2.1's "entire tracked
  universe"** — recorded in DEV-PLAN Appendix C (amendment 2026-08-16),
  decided by the product owner in the 3.1 spec discussion; surface to the
  trader alongside the first FlowShare numbers rather than blocking on it.
  Numerators keep **full** basket membership, so overlapping baskets'
  shares can sum >100%; that is documented, not hidden (the disjoint-set
  treatment for cross-basket narrative is 3.7's). The zero-sum caveat goes
  in the package doc verbatim: shares are zero-sum only *inside* the
  tracked universe — flow leaving the universe entirely redistributes
  shares misleadingly (mitigated by 3.7's de-grossing precedence).

- **D2 — Share profiles: same nightly run, same estimator, new derived
  series.** Per-ticker volume profiles cannot produce a share baseline:
  medians don't pass through division (median of daily ratios ≠ ratio of
  summed medians), and share σ is dominated by basket↔universe co-movement
  (tape doubles → share unmoved) that per-ticker σs cannot see. So
  `cmd/profiles`, in the same run, computes per basket per minute each of
  the 20 days' FlowShare from the bucket files, then median and
  MAD×`profile.MADConsistency` over those 20 values. Output:
  `data/profiles/baskets/<basket>.csv`, one row per minute (570..959),
  usual conventions (self-describing header, atomic tmp+rename, `fnum`
  formatting, byte-deterministic, contiguity-validated reader).

- **D2a — Stamped, self-invalidating cache.** The CLAUDE.md invariant
  ("profiles are stored per ticker, never per basket") protects history
  from membership edits; these files honor its intent as a *derived cache*:
  the per-ticker profiles and bucket files remain the only stored truth,
  and each basket file's header comment records the build inputs **and the
  sorted member list**. The reader refuses a file whose recorded membership
  differs from the current config — a basket edit can never leave a
  silently stale baseline; the remedy is the cheap nightly rebuild command.

- **D2b — Member-coverage policy (missing-member days).** The membership
  stamp (D2a) guards against config edits, not against coverage drift
  inside the 20 bucket files: a member added to the universe later has no
  rows in older files, and the bucket reader's zero-materialization makes
  "absent from that day's capture" indistinguishable from "didn't trade" —
  the day's share sample would compute without the member, biased low,
  silently. Policy: a member with **zero prints across a day's entire
  regular session** is *uncovered* for that day, and that **entire day is
  skipped for every basket** — an uncovered member corrupts the common
  denominator, so a per-basket skip would still bias every other basket's
  share that day. (Among 164 liquid members, all-session silence is
  overwhelmingly "not captured", and a false skip errs toward silence —
  D3's <10-day rule then gates the z.) The build prints skipped days with
  the symbols that caused them. Known limitation, recorded here: this
  also skips a legitimately halted-all-day member's day; the real fix is
  effective-date membership (backlog: universe loader hardening). Note
  the same drift bias exists, unhandled, in per-ticker volume profiles
  (`Row.Days` is unconditional) — currently moot since all 21 bucket
  files share one universe; noted on that backlog entry, not fixed here.

- **D3 — Defined nulls.** A day whose universe counted $vol is 0 in a
  minute contributes **no sample** to that bucket (0/0 is not a zero
  share); the row records its actual sample count. A basket with <10
  sampled days at a minute renders a z gap (2.1's ≥10-day rule at basket
  level). All z nulls flow from `zguard.Z` — never an exception, never Inf.

- **D4 — σ guard, new floor family.** `sigma_floor_flowshare(minute) =
  frac × median across baskets of σ_share(B, minute)`, where the median is
  taken over baskets with a **defined** σ at that minute (≥1 sampled day
  after D2b/D3 skips); if no basket has one, the floor is 0 and every z at
  that minute nulls via `zguard.Z`'s 0/0 rule — a defined gap, never an
  invented floor. Same `-sigma-floor-frac` flag, recomputed with every
  build, written as a new column of `_floors.csv` (readers map columns by
  name; this reader now requires the new column — same-repo readers update
  in this PR).

- **D5 — What renders (dev-view columns via the registry only).**
  `share` — current in-progress minute, live: a ratio is meaningful
  intra-minute because numerator and denominator cover the same window.
  `shareZ` — last **completed** minute only, matched bucket, through the
  guard. `conc` — top member's share of basket counted $vol for the
  completed minute, rendered as symbol + percent (`NVDA 63%`); a statement
  of measurement. **Render nulls:** universe counted $vol of 0 in the
  window → `share` (and `shareZ`) render the gap, never `0%`; basket
  counted $vol of 0 → `conc` renders the gap ("NVDA 0%" would be a fake
  statement) — pre-open renders hit both paths every time. **Determinism:**
  `conc` ties break alphabetically (first-wins over the sorted member
  list). The clock-line legend gains a clause naming which minute each new
  column describes (share = in-progress; shareZ/conc = completed), same as
  the existing columns. **Deviations from A8, explicit:** A8 says "always
  computed and persisted" and "rendered when >50%" — persistence rides 4.1
  (nothing else persists metrics yet either), and the >50% render gate
  belongs to the 5.1 tile display; the dev view shows `conc` always (it is
  the learning instrument). The ex-leader flow series (3.7's
  degeneracy-guard input) rides 3.7.

- **D7 — Since-open cumulative share (added 2026-08-16, product owner).**
  The per-minute z is the atom 3.7's CUSUM needs, but it flickers minute to
  minute; the morning's *story* is the cumulative share: "basket B has
  taken X% of the tape so far today vs a typical Y% by this time."
  Definition: counted $vol(B) / counted $vol(union) over
  `[open, end of last completed minute)`, clamped at the close — displayed
  value, typical, and z all cover the identical window so the operands
  reconcile. Baseline: a second share family in the same basket files —
  per minute, each day's cumulative-through-that-minute share, then
  median/MAD over days (same medians-don't-commute reason); a day samples
  a minute only when its cumulative universe $vol is >0. Its own floor
  family `sigma_floor_cumshare` (cumulative shares are far less volatile
  than per-minute shares; borrowing the per-minute floor would over-damp).
  Renders as `cum_share` / `cum_share_typ` (20d median) / `cum_share_z`,
  gap before the first completed session minute; same 10-day gate.

- **D6 — Homes.** Share-profile build + floor extension: `internal/profile`
  (they are profile outputs of the same nightly run). Runtime metric:
  new `internal/flowshare` (share, z, concentration from store + share
  profiles + floors + zguard). Wiring: dev-view column registry only —
  no renderer or command changes beyond registration.

## Done when (all on replayed recorded data)

1. Unit: synthetic two-basket universe with hand-computable numbers —
   share, μ, MAD, and z exact; null paths exercised (0/0 day skipped,
   <10 days → gap, MAD=0 basket bounded by the share floor).
2. Share profiles for all 22 baskets build from the real 20 bucket files
   in the same `cmd/profiles` run; two runs byte-identical; the
   stale-membership refusal has a test (edited config → reader error
   naming the basket).
3. On the 2026-08-14 replay, `share`/`shareZ`/`conc` populate for all 22
   baskets; one basket × minute's shareZ verified by independent
   recomputation from bucket files + share-profile CSV. The share profiles
   for this run are built **`-through 2026-08-13`** — the replayed day
   must be excluded from its own baseline (same rule as the 2.1 RVOL
   check; `cmd/profiles` has `-through` for exactly this).
4. The overlap effect is measured and reported (Σ shares across baskets at
   a few minutes — expected >100% by construction), recorded in the story
   close notes, not hidden.
5. (D7) The cumulative columns populate on the 08-14 replay and one
   basket's `cum_share_z` is verified by independent recomputation — with
   the recomputation restricted to the captured span: this capture starts
   11:51 ET, so its "since open" window is missing the morning while the
   baseline is full-day cumulative; the code is correct, the data partial.
   The first honest full-day cum read is the first full-session capture.
